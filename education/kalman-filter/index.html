An intro to Kalman filters

Here is the whole idea of a Kalman filter in one paragraph:

A Kalman filter repeats two steps forever. First, predict: take your last estimate of where something was and how it was moving, along with how sure you were of it, and roll it forward to now, growing less sure as you go. Then correct: compare that prediction with a noisy new measurement and blend the two, trusting whichever is less uncertain. Out comes a new estimate of where it is now, and how sure you are of it.

That's it. Everything else is making each phrase precise. This post does exactly that: below is a complete constant-velocity Kalman filter for one object moving in 2D, in about 40 lines of NumPy, and each section takes one phrase of that paragraph and shows the equation and the line of code that implement it. At the end, a single table lines all three up.

import numpy as np

H = np.array([[1., 0, 0, 0],
              [0., 1, 0, 0]])

class Track:
    def __init__(self, z, t, pos_sd=1.0, vel_sd=5.0, accel_sd=0.5):
        self.x = np.array([z[0], z[1], 0.0, 0.0])     # where it was, how it was moving
        self.P = np.diag([pos_sd**2, pos_sd**2, vel_sd**2, vel_sd**2])  # how sure
        self.t = t
        self.q = accel_sd**2

    def predict(self, t):
        dt = t - self.t
        if dt < 0:
            raise ValueError("out-of-order measurement: buffer or reject")
        F = np.eye(4); F[0, 2] = F[1, 3] = dt
        G = np.array([[dt**2 / 2, 0], [0, dt**2 / 2], [dt, 0], [0, dt]])
        Q = self.q * G @ G.T
        self.x = F @ self.x                           # roll it forward to now
        self.P = F @ self.P @ F.T + Q                 # growing less sure as you go
        self.t = t

    def innovation(self, z, R):
        r = z - H @ self.x                            # compare prediction with measurement
        S = H @ self.P @ H.T + R
        d2 = r @ np.linalg.solve(S, r)
        return r, S, d2

    def update(self, z, R, gate=9.21):
        r, S, d2 = self.innovation(z, R)
        if d2 > gate:
            return False
        K = self.P @ H.T @ np.linalg.inv(S)           # trust whichever is less uncertain
        self.x = self.x + K @ r                       # blend the two: new estimate
        I_KH = np.eye(4) - K @ H
        self.P = I_KH @ self.P @ I_KH.T + K @ R @ K.T # how sure you are now
        return True

One bit of notation first, because it's exactly what the paragraph's "last", "prediction" and "now" are tracking. Measurements arrive at times $k = 1, 2, 3, \dots$ Each estimate gets a superscript for which moment it describes:

  • $x^+_{k-1}$: the estimate right after the last correction. "Your last estimate."
  • $x^-_k$: that estimate rolled forward to the new measurement's time, before looking at the measurement. "That prediction."
  • $x^+_k$: after blending in the measurement. "A new estimate of where it is now."

The covariance $P$ gets the same marks. The code has only one self.x and one self.P, and they move through these three moments in turn: predict turns a $+$ into a $-$, and update turns the $-$ back into a $+$. Then the new estimate becomes the next step's "last estimate", and the loop repeats forever.

Let's go phrase by phrase.

"Where something was and how it was moving"

self.x = np.array([z[0], z[1], 0.0, 0.0])

The state $x$ is everything we want to know about the object, packed into one vector. "Where it was" is position, and "how it was moving" is velocity:

$$ x = \begin{bmatrix} p_x & p_y & v_x & v_y \end{bmatrix}^T $$

Position in metres, velocity in metres per second, all in one fixed world frame. The order matters only in that every matrix below has to agree with it. A surprising number of tracker bugs are a matrix written for [px, vx, py, vy] multiplying a state stored as [px, py, vx, vy].

The "how it was moving" half is the important one. It's what makes "roll it forward to now" possible. And notice that our sensor never measures it: it only gives position $z = [p_x, p_y]$. The filter has to infer velocity from how positions change over time. This gap between what you measure and what you want to know is the reason the filter exists. If you could measure the full state perfectly, you wouldn't need one.

The very first "last estimate" has to come from somewhere, so we start the track from the first measurement: position is the measured position, and velocity is zero. Zero isn't a belief that the object is stationary. It's a placeholder, and the next phrase says how little we trust it.

"How sure you were of it"

self.P = np.diag([pos_sd**2, pos_sd**2, vel_sd**2, vel_sd**2])

A Kalman filter never carries just a guess. It carries a guess and a covariance $P$ that says how wrong the guess might be. "How sure" is $P$, and it shows up in the paragraph three times: how sure you were, growing less sure, and how sure you are now. The diagonal holds variances (standard deviation squared, a classic place to drop a square). The off-diagonals hold how errors in different components move together.

Here we're fairly sure of position (1 m, about the sensor noise) and very unsure of velocity (5 m/s). That large velocity variance is what lets the first few measurements set the velocity quickly. If you initialized velocity to zero with a small variance, the filter would believe its own made-up number and ignore the data for a long time.

It starts diagonal, meaning no correlation between position and velocity errors. That changes after the very first predict, and it turns out to be the most important thing in the whole filter.

"Roll it forward to now"

F = np.eye(4); F[0, 2] = F[1, 3] = dt
self.x = F @ self.x

"Now" is the time of the new measurement, and "roll forward" means: assume constant velocity, so position moves by velocity times elapsed time and velocity stays put. That's all $F$ says:

$$ x^-_k = F\,x^+_{k-1}, \qquad F(\Delta t)= \begin{bmatrix} 1&0&\Delta t&0\\ 0&1&0&\Delta t\\ 0&0&1&0\\ 0&0&0&1 \end{bmatrix} $$

The first row reads $p_x \leftarrow p_x + \Delta t \, v_x$. Note that dt is computed from timestamps, not assumed. Sensors drop frames and arrive irregularly, and a filter with a hard-coded dt = 0.1 silently goes wrong the moment they do.

if dt < 0:
    raise ValueError("out-of-order measurement: buffer or reject")

"Forward" is literal. If a measurement shows up older than the current state (common with sensors that have processing latency), you need a policy: buffer and re-order, re-run the filter from that time, or drop it. Predicting backwards by accident is a silent bug, so make it a loud one.

"Growing less sure as you go"

G = np.array([[dt**2 / 2, 0], [0, dt**2 / 2], [dt, 0], [0, dt]])
Q = self.q * G @ G.T
self.P = F @ self.P @ F.T + Q
$$ P^-_k = F\,P^+_{k-1}\,F^T + Q $$

The uncertainty rolls forward too, and it gets worse in two ways. $FPF^T$ carries the existing uncertainty through the motion: if we're unsure of velocity, we become unsure of position, more so the longer we wait. This term also creates the position–velocity correlation in the off-diagonals. After a predict, the filter "knows" that if position turns out further along than expected, velocity was probably higher than expected. Hold on to that; it's how velocity gets learned.

The second term, $Q$, is the honest admission that the object doesn't really move at constant velocity. Imagine a random, unknown acceleration $a$ with variance $q$ acting over the interval. It shifts position by $\tfrac{1}{2} a \Delta t^2$ and velocity by $a \Delta t$. The columns of $G$ are exactly those two effects, one column per axis, so $Q = G\,q\,G^T$ is the covariance of where that random push could have sent us. Since it depends on $\Delta t$, "as you go" is literal too: a long gap adds a lot of doubt and a short one adds a little.

accel_sd is the main tuning knob of the filter. Too small and the filter is stubborn: it lags behind a turning object and can end up rejecting the true measurements. Too large and it's twitchy: the velocity estimate chases every bit of noise. You'll see the twitchy version in the run below.

"A noisy new measurement"

Two things describe the measurement: its value $z_k$, and how noisy it is, the covariance $R$. Here $R = I \cdot (1\text{ m})^2$: each position fix is off by about a metre. (Variances again, not standard deviations.) $R$ is passed into update with each measurement, so different sensors, or the same sensor on a bad day, can say how noisy they are.

The paragraph says "of where it is" for a reason, too: the sensor sees only part of the state. $H$ is the matrix that picks out that part, "what the sensor would see if our state were true":

$$ H= \begin{bmatrix} 1&0&0&0\\ 0&1&0&0 \end{bmatrix} $$

It reads off position and ignores velocity.

"Compare that prediction with the measurement"

r = z - H @ self.x
S = H @ self.P @ H.T + R
$$ r_k = z_k - H\,x^-_k, \qquad S_k = H\,P^-_k\,H^T + R $$

The comparison is a subtraction. The innovation $r$ is the surprise: what we measured minus what we predicted we'd measure. If the filter is doing well, innovations look like small, zero-mean noise.

$S$ is how big we expected the surprise to be. It has two sources: our own doubt in the predicted position ($HP^-H^T$, the position block of $P^-$) plus the sensor's noise $R$. A big innovation is only alarming relative to $S$.

d2 = r @ np.linalg.solve(S, r)

Which is exactly what this measures. $d^2 = r^T S^{-1} r$ is the squared Mahalanobis distance: the surprise measured in units of expected surprise. Being 3 m off when we expected ±0.5 m is a much bigger deal than 3 m off when we expected ±5 m, and $d^2$ captures that in one number. (solve instead of inv is just the numerically nicer way to compute $S^{-1}r$.)

The fine print: the gate

if d2 > gate:
    return False

The paragraph quietly assumes every measurement is real. In practice some aren't. If the filter's model is right, $d^2$ for a 2D measurement follows a chi-square distribution with 2 degrees of freedom. That gives a principled threshold: 99% of genuine measurements have $d^2 < 9.21$ (95% have $d^2 < 5.99$). Anything beyond the gate is far more likely to be a glitch, a reflection, or a different object than our target, so we refuse to blend it in. The prediction stands as the new estimate, and the caller counts it as a miss.

Without this, one bad measurement yanks an established track off course. With it, the track ignores the outlier and keeps going.

"Trusting whichever is less uncertain"

K = self.P @ H.T @ np.linalg.inv(S)
$$ K_k = P^-_k\,H^T S_k^{-1} $$

This is the heart of it. The Kalman gain $K$ is "how much to trust the measurement", computed from the two uncertainties. It's easiest to see in one dimension, where it collapses to:

$$ K = \frac{\sigma^2_{\text{pred}}}{\sigma^2_{\text{pred}} + \sigma^2_{\text{meas}}} $$

If the prediction is very uncertain ($\sigma^2_{\text{pred}}$ large), $K \to 1$: trust the measurement. If the sensor is very noisy ($\sigma^2_{\text{meas}}$ large), $K \to 0$: trust the prediction. In between, each side is weighted by how unsure the other side is. That's the phrase, exactly.

In the matrix version, $K$ is $4\times 2$: it maps a 2D position surprise into a correction for all four state components. And here's where the off-diagonals of $P$ pay off. Because predict made position and velocity errors correlated, $PH^T$ has non-zero velocity rows, so a position surprise also corrects velocity. Measured further ahead than expected? Then you were probably faster than you thought. That's how a filter that only ever sees positions learns "how it was moving".

"Blend the two" into "a new estimate of where it is now"

self.x = self.x + K @ r
$$ x^+_k = x^-_k + K_k\,r_k $$

Start from the prediction and move a fraction $K$ of the way toward the measurement. In one dimension this is literally a weighted average, $x^+ = (1-K)\,x^- + K\,z$. That's all a Kalman filter is: a running weighted average with the weights computed for you.

"And how sure you are of it"

I_KH = np.eye(4) - K @ H
self.P = I_KH @ self.P @ I_KH.T + K @ R @ K.T
$$ P^+_k = (I - K_k H)\,P^-_k $$

Blending in information always makes you more sure, so $P$ shrinks. In one dimension, $\sigma^2_{\text{new}} = (1-K)\,\sigma^2_{\text{pred}}$, which is smaller than either input variance. The code uses the "Joseph form", which is algebraically the same as the equation above but stays symmetric and positive-definite under floating-point round-off. Same math, fewer mysterious failures after a million updates.

And that closes the loop: $x^+_k$ and $P^+_k$ become the next step's "last estimate" and "how sure you were".

Run it

To try it, simulate an object moving at a constant $(2, 1)$ m/s, measured with 1 m noise at irregular intervals of 0.3–0.7 s. Delete the measurements between 8 s and 11 s to make a gap, and push one measurement 30 m off to make an outlier:

rng = np.random.default_rng(0)
v_true = np.array([2.0, 1.0])
times = np.cumsum(rng.uniform(0.3, 0.7, size=40))
times = times[(times < 8) | (times > 11)]
R = np.eye(2) * 1.0**2

trk = None
for i, t in enumerate(times):
    z = v_true * t + rng.normal(0, 1.0, size=2)
    if i == 25:
        z = z + np.array([30.0, -30.0])
    if trk is None:
        trk = Track(z, t)
        continue
    trk.predict(t)
    sd_before = np.sqrt(trk.P[0, 0])
    ok = trk.update(z, R)
    sd_after = np.sqrt(trk.P[0, 0])
    print(f"t={t:5.2f}  v=({trk.x[2]:+.2f}, {trk.x[3]:+.2f})  "
          f"pos_sd {sd_before:.2f} -> {sd_after:.2f}  {'ok' if ok else 'REJECTED'}")

Each line prints the paragraph's quantities: v is "how it was moving" from the new estimate $x^+_k$; the first pos_sd is the position standard deviation after "growing less sure" (from $P^-_k$), and the second is "how sure you are" after correcting (from $P^+_k$). Here's the output (trimmed):

Every phrase shows up:

  • "How it was moving" is learned, never measured. The first velocity, $(5.67, -0.54)$, is junk. It comes from two noisy points 0.4 s apart, and 1 m of noise over 0.4 s is several m/s of velocity noise. Within a few seconds it settles near the true $(2, 1)$.
  • "Growing less sure", then "how sure you are". Every row, pos_sd grows during predict and shrinks on correction. It levels off around 0.64 m after correction, below the 1 m sensor noise, because the filter is blending many measurements through the motion model.
  • "As you go" scales with time. After the 3.65 s gap the predicted standard deviation is 4.02 m. There was no fake measurement and no zeros, just a long roll-forward with growing doubt. Now the prediction is the uncertain side, so "trusting whichever is less uncertain" means a big gain, and one measurement pulls the doubt back to 0.97 m.
  • The gate's fine print. At 16.80 s the 30 m jump is rejected. Velocity is unchanged and pos_sd stays at its predicted value, because nothing was blended in.
  • How much doubt "as you go" adds is a choice. The velocity keeps wandering by about half a metre per second even late in the run. That's the twitchy filter: accel_sd=0.5 says the object might be accelerating, so predictions are doubted more and measurements trusted more, noise included. This simulated object really is constant, so with accel_sd=0.05 the final velocity is $(1.97, 0.97)$ and pos_sd drops to about 0.42 m. A real boat or car turns, though, and that small value would lag every turn. Picking $Q$ is a statement about how your object actually moves.

Real stuff

The paragraph is the same for every Kalman filter. What changes in real systems is what each phrase has to contend with:

"A noisy new measurement" is rarely a clean position. Our toy sensor hands over 2D positions. Real ones don't:

SensorGives youDoesn't give you
CameraBearing (direction), appearance, classDistance from a bounding box alone. Range needs a known object size, geometry, motion over time, or another sensor.
RadarRange and bearing; sometimes range rate (Doppler)Full velocity. Doppler only sees the component of motion toward or away from you.
LiDARRange and 3D shape, at short rangeObjects. Raw points must be clustered first.
IMUYour own rotation rate and accelerationAnything about other objects, or drift-free position.
GPSYour own position and velocityCertainty. Its error leaks into every object you place on the map.

"Of where it is" can be nonlinear. Radar measures range $\sqrt{\Delta x^2+\Delta y^2}$ and bearing $\operatorname{atan2}(\Delta y, \Delta x)$, which aren't linear in the state, so a single matrix $H$ can't describe them. The extended Kalman filter (EKF) swaps $H$ for the Jacobian of the measurement function at the current prediction. Every other phrase is unchanged. (Remember to wrap bearing innovations into $[-\pi, \pi]$.)

"Where" depends on a frame. We assumed one fixed world frame. A sensor on a moving vehicle measures relative to itself, so each measurement has to be moved into the world frame using the vehicle's pose: $p_{\text{world}} = R(\psi)\,p_{\text{vehicle}} + t$. Get that wrong and a stationary buoy appears to swing around every time your boat turns.

"Now" means capture time. The pose and the roll-forward must use the moment the measurement was captured, not when it arrived. At a 10°/s turn, a 50 ms timestamp error is a 0.5° bearing error, which is about 1.7 m sideways at 200 m range. With several sensors at different rates, you process each measurement in capture-time order, each with its own $H$ and $R$. You don't pair up "latest readings".

"Something" is usually many things. The paragraph assumes you know which measurement belongs to which object. Deciding that is a separate problem called data association. The usual loop is: roll every track forward, compute $d^2$ between every track and every detection, gate, assign one-to-one (for example with scipy.optimize.linear_sum_assignment), correct the matched tracks, coast the unmatched ones, and start tentative tracks from leftover detections. The innovation method above, which does the "compare" step without blending, is the piece that plugs into that loop.

FAQ

What if no measurement arrives? Then you do the first half of the paragraph and skip the second: roll forward, grow less sure, done. The state coasts on the motion model and $P$ grows, which also widens the gate so the object can be picked up again. Never fill the gap with zeros or a repeated last value. If a track goes too long without a correction, delete it.

What does a bigger $R$ do? The measurement becomes the more uncertain side, so "trusting whichever is less uncertain" leans on the prediction: $S$ grows, $K$ shrinks, and each measurement moves the estimate less. You get a smoother estimate that reacts more slowly.

How do I know if $Q$ and $R$ are right? Watch the comparisons. If the filter's "how sure" is honest, $d^2$ averages about the measurement dimension (2 here). Consistently bigger means the filter is overconfident, so raise $Q$ or $R$. Consistently smaller means it's too cautious.

Isn't this just an exponential moving average? "Blend the two" with a fixed weight is an EMA, and for a single state with fixed noise the gain settles to a constant, so it nearly is one. The Kalman filter earns its keep when the weight shouldn't be fixed, or when you need something an EMA doesn't give you: velocity you never measured, prediction through gaps, irregular timing, uncertainty you can gate on, and a principled way to combine sensors with different noise. If you only need to smooth a number on a display, an EMA is fine.

Do I need an EKF to fuse two sensors? No. Two sensors just means two kinds of "noisy new measurement", each with its own $H$ and $R$, correcting the same state. You need an EKF (or an unscented filter) when "of where it is" is a nonlinear function of the state, like range and bearing.
